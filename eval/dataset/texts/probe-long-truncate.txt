这篇把「从零写一个迷你 LSM 键值存储引擎」的完整过程拆开讲，语言用 Go，目标是一个能在单机上跑、支持崩溃恢复和事务的最小实现。它不是生产级数据库，但每一个决策都对应真实数据库里同样的取舍，跟着走一遍能把这些取舍看明白。

先说目标与范围。我们要实现的是「有序键值存储」，接口只有四个：Put(key, value)、Get(key)、Delete(key)、Scan(start, end)。键和值都是字节数组，键在内部按字节序排序。范围之外的东西明确不做：不做 SQL 层，不做网络协议，不做多机复制，不做二级索引。把范围钉死，是为了让剩下的部分每一块都能讲透。

整体架构分三层。最上层是内存里的可变结构 MemTable，用跳表（skip list）实现，负责承接所有写入并保持有序。中间层是只读的不可变文件 SSTable，写入时由 MemTable 冻结后落盘生成，文件内部按 key 有序排列，并附带索引块和布隆过滤器。最下层是预写日志 WAL（Write-Ahead Log），每次写入先追加到 WAL 再改 MemTable，保证进程崩溃后能重放。

数据在磁盘上的编码格式决定了很多性能上限，所以先把格式定下来。WAL 的每条记录布局是：4 字节 CRC32、2 字节记录类型（0 表示 Put，1 表示 Delete）、4 字节 key 长度、4 字节 value 长度、key 字节、value 字节。加 CRC 是为了在断电导致半条记录写下去时，能在恢复阶段把这条残缺记录识别出来并丢弃。没有 CRC，恢复时会把半截 key 当成完整 key，产生永远删不掉的脏数据。

SSTable 的文件布局自尾向前是：数据块（data block）、索引块（index block）、布隆过滤器（bloom filter）、元数据块（footer）。footer 固定 48 字节，末尾 8 字节存索引块和布隆过滤器的偏移与长度，最后 8 字节存一个魔数（magic number）。读文件时先读末尾 48 字节，校验魔数，再据此定位索引块。这样不需要维护额外的外部文件，一个 SSTable 就是自包含的。

索引块存的是「每个数据块的第一条 key」到「该块在文件中的偏移」的映射。查找某个 key 时，先在索引块里二分，定位到可能包含它的数据块，再把整块读进内存扫描。块大小默认 4KB，这个值直接决定读放大：块越大，一次读进来的无用数据越多；块越小，索引块越大，内存里常驻的索引就越大。实测在机械盘上 4KB 到 16KB 差别不大，在 NVMe 上 4KB 明显更划算。

布隆过滤器解决的是「这个 key 肯定不在这个文件里」的判断。它的原理是把 key 经过 k 个哈希函数映射到位数组的 k 个位上，全为 1 才「可能存在」，任何一位为 0 就「一定不存在」。关键参数是位数组大小 m、哈希个数 k 和元素个数 n 的关系，误判率约等于 (1 - e^(-kn/m))^k。我们默认每条 key 分配 10 个 bit、k 取 7，对应误判率大约 1%。误判只影响性能（多读一个文件），不会影响正确性，因为它只会说「可能存在」。

写入路径的每一步都要想清楚顺序。一次 Put 的顺序是：先组装记录、追加写 WAL、按 fsync 策略决定是否落盘、再插入 MemTable、最后返回成功。顺序不能颠倒：如果先改 MemTable 再写 WAL，那么在两步之间崩溃，内存里的修改会随进程一起消失，而磁盘上没有任何痕迹，这条写入就丢了。先写 WAL 再改内存，最坏情况只是重放一遍，结果幂等。

fsync 策略是这套引擎里最直接的性能旋钮。每次写入都 fsync，单条写入延迟从微秒级跳到毫秒级，机械盘上能到 10ms 以上，吞吐直接掉两个数量级。完全不 fsync，操作系统把数据留在页缓存里，进程崩溃不丢（因为内核还持有），但机器断电会丢最近几秒的写入。我们默认取中间路线：每 200 次写入或每 100ms 触发一次 fsync，用后台线程做。这个折中的含义是「断电最多丢 100ms 的写入」，对多数应用可接受。

MemTable 用跳表实现，理由是跳表的插入和查找都是 O(log n)，且天然有序，遍历就是顺序读，省掉了平衡树的旋转逻辑。跳表的层数用随机函数决定，每层向上晋升的概率取 0.25。实测这个概率在 0.25 到 0.5 之间时性能差异不大，取 0.25 内存更省。跳表节点的 key 直接引用用户传入的字节切片，不再复制一遍，减少一次分配，但要约定调用方不能改这块内存。

MemTable 有一个内存上限，默认 64MB，达到上限就冻结成不可变 MemTable，另起一个新的可变 MemTable 继续写。冻结的动作很快，只是把指针换掉，新的写入立刻可以进新表。后台线程负责把不可变 MemTable 落盘成 SSTable，落盘期间用户写入不受影响。这个「前台不停、后台慢工」的结构是 LSM 能扛住写吞吐的根本原因。

落盘时有一个必须做的优化：把不可变 MemTable 的有序遍历直接写成文件，不要先排序。跳表本身已经有序，按中序遍历就是全局升序，落盘就是一次顺序写。如果用一个无序的哈希表做内存表，落盘前就得排序，几十 MB 的数据排序要几百毫秒，还会阻塞后台线程。这也是选跳表而不是哈希表的原因之一。

SSTable 写完后要做一次原子替换。做法是先写到一个临时文件（如 000123.sst.tmp），写完全部数据、fsync、再 rename 成 000123.sst。rename 在同一个文件系统内是原子的，所以不存在「半个 SSTable 被当成完整文件读」的状态。这一步不能省，否则进程在落盘中途被杀，恢复时会把残缺文件当有效文件，读到一堆乱码。

读路径要按代价从低到高依次尝试。第一步查可变 MemTable，第二步查所有不可变 MemTable（通常只有一个），第三步才去查 SSTable，从新到旧。查每个 SSTable 时先用布隆过滤器筛一遍，判定「一定不在」就直接跳过，判定「可能存在」才去读索引块和数据块。一个典型的读请求在热数据上命中 MemTable，延迟在微秒级；冷数据要穿透到最旧的文件，延迟在毫秒级。

读放大是 LSM 与 B 树最本质的差别。B 树一次查找只读一个节点，但每次写入要原地改页，写放大高、并发难做。LSM 每次写入只追加，写放大低，代价是一次读可能要查多个文件。这个取舍换来的是写吞吐和顺序写，代价是读延迟。理解这一点，就能理解为什么写密集型的场景（日志、时序、消息）偏爱 LSM，而读密集且要求低延迟的场景偏爱 B 树。

Compaction（合并）是把读放大控制在可接受范围的机制。后台线程定期挑选若干 SSTable 合并成一个，合并时按 key 归并、同一 key 只保留最新的版本、被删除的 key 在足够旧之后彻底丢弃（墓碑清除）。合并后文件数变少，读路径要查的文件数随之变少。没有 compaction，文件会越来越多，读会越来越慢，最终不可用。

合并策略有两种典型选择。一种是分层合并（leveled compaction），把文件按大小分层，每层内 key 范围不重叠，读最多查每层一个文件，读放大可控但写放大高。另一种是大小分层合并（tiered / size-tiered），同层内允许重叠，写放大低但读放大高。我们默认用分层合并，因为单机场景读延迟更敏感。层数默认 7 层，每层容量按 10 倍递增。

合并时的空间开销要提前算好。把两个各 100MB 的文件合并，需要临时占用 200MB 左右的空间（读旧文件、写新文件），完成后再删旧文件。如果磁盘水位已经到 95%，合并会因为空间不足失败，然后重试失败，形成死循环。工程上要预留出「最大层容量的一倍」作为合并余量，磁盘告警水位不要等到 90% 以上。

崩溃恢复的流程是重放 WAL。进程启动时扫描 WAL 目录，按编号从小到大读取每条记录，校验 CRC，把完整的记录按顺序重新插入新的 MemTable。遇到 CRC 校验失败的记录就停止，丢弃它以及它之后的所有内容（因为那说明断电发生在这一条写入的中间，后面的记录也不完整）。恢复完成后立刻把 MemTable 落盘成 SSTable，再清空已重放的 WAL，避免下次启动重复重放。

墓碑（tombstone）是删除的实现方式。Delete 不真的去文件里找那条记录删掉，而是写一条类型为 1 的记录，value 为空。读的时候如果读到最新的版本是墓碑，就返回「不存在」。墓碑只有在合并时遇到更旧的数据、且确定没有更老的未合并层还持有这条 key 时，才能被丢弃。如果过早丢弃墓碑，一条被删的 key 会在更旧的文件里「复活」，这是 LSM 里最经典的 bug 之一。

事务用 MVCC（多版本并发控制）实现。每条记录带一个递增的序列号（sequence number），写事务在提交时分配一个序列号，读事务在开始时取一个快照序列号，只看到序列号小于等于自己的版本。这样读不阻塞写、写不阻塞读。默认隔离级别是可重复读（repeatable read），因为快照读天然满足它。要支持串行化，得再加一层冲突检测，我们不做，明确写在文档里。

快照与迭代器是 MVCC 的配套能力。创建一个快照后，迭代器在该快照上遍历所有 key，期间即使有新的写入或删除，迭代器看到的内容也不变。实现上是给迭代器绑定一个序列号，遇到版本号大于自己的记录就跳过。代价是旧版本不能立刻回收，所以需要一个后台线程定期清理「没有活跃快照引用」的旧版本，否则磁盘会持续膨胀。

数据压缩能显著降低磁盘占用和 I/O 量，但会消耗 CPU。我们默认关闭压缩，只提供一个开关。原因是压缩算法（如 Snappy、Zstd）的收益高度依赖数据本身：日志类文本能压到三成，随机二进制几乎压不动。如果默认开启，用户拿到一个 CPU 翻倍、磁盘没省多少的结果，会以为是引擎有问题。把它做成显式开关，让用户自己按数据特征决定。

块缓存（block cache）缓存的是热点数据块，而不是整个文件。默认大小 128MB，用 LRU 淘汰。缓存命中时读路径跳过磁盘 I/O，直接返回内存里的块。缓存大小的经验值是「热数据集大小」的 1.5 到 2 倍，太小会频繁淘汰导致命中率低，太大则会挤占进程其他部分的内存，还可能触发操作系统的 OOM killer。我们在配置里把它做成可调项，并打印命中率方便观察。

配置参数的默认值要能覆盖多数场景，同时每一项都要有注释说明「调大调小的后果」。举几个关键的：MemTable 上限 64MB（调大减少文件数但增加恢复时间）、块大小 4KB（调大减少索引内存但增加读放大）、布隆过滤器 bits 10（调大降低误判但增加内存）、fsync 间隔 100ms（调大提升吞吐但增加断电丢数据窗口）、合并线程数 2（调大加速合并但抢占 I/O）。这些参数没有普适最优值，只有「对你的负载更合适」。

基准测试的数据要如实给出测试条件，否则数字没有意义。在我们的测试机上（4 核、16GB 内存、SATA SSD），顺序写吞吐约 12 万条每秒（每条 100 字节，fsync 间隔 100ms），随机写约 8 万条每秒，随机读命中缓存约 30 万次每秒，未命中约 1.2 万次每秒。这些数字跟硬件强相关，换到 NVMe 上未命中读能提升一个数量级。写下来是为了让人有量级感，不是让人拿去当宣传。

常见坑里最隐蔽的是「时间戳与序列号混用」。有人图省事，用挂钟时间当版本号，结果同一毫秒内发生了两次写入，两个版本号相等，读的时候分不清哪个更新，于是读到旧值。正确做法是用单调递增的整数序列号，落盘时把「当前最大序列号」也写进元数据，重启后从这里继续递增，绝不依赖挂钟。

第二个坑是「key 太长」。键是按字节比较的，长键会同时抬高索引大小、布隆过滤器的内存、比较开销。见过用完整 URL 当 key 的系统，索引块比数据块还大。工程上的做法是对长 key 做一次哈希，把哈希值作为实际存储的 key，原文单独存，读的时候再取回来。代价是多一次查表，收益是索引和比较都回到常数级。

第三个坑是「删除与范围扫描的交互」。Scan 在遍历时如果遇到墓碑，要跳过这条 key，但如果同一条 key 在更旧的文件里有活版本，就要让墓碑生效、不返回旧值。这要求迭代器在跨文件合并遍历时严格按序列号去重，只保留最新版本。实现里这是最容易写错的一段，务必为它单独写测试：写入、删除、再扫描，断言结果为空。

排查手册第一条：写入吞吐突然掉下来。先看是不是在 compaction。合并会大量占用磁盘带宽，此时写入的 fsync 会排队变慢。判断方法是看合并线程的活动，以及磁盘 util 是否接近 100%。如果是，考虑调低合并线程数或把它放到低峰期。不要一上来就怀疑代码，先看磁盘。

排查手册第二条：读延迟突然变高。先看文件数。文件数多说明 compaction 没跟上，读要查的文件变多。再看缓存命中率，命中率掉下来说明热数据集变大了，或者缓存被别的部分挤占。这两条排查完再去看布隆过滤器的误判率，如果误判率异常高，可能是位数组参数配错了，或者 key 分布有规律导致哈希聚集。

排查手册第三条：进程启动特别慢。这是恢复阶段的典型症状。恢复时间约等于「WAL 总大小 / 磁盘顺序读速度」加上「重放写入的速度」。WAL 太大通常是因为 fsync 间隔太长、或者落盘线程卡住导致 WAL 一直没被清理。缩短 fsync 间隔、确认后台落盘线程没死，是两条直接的缓解手段。

扩展方向有几个可以按需做。加一个 TTL 层，让记录带过期时间，扫描时跳过过期项；加一个前缀扫描的优化，让 Scan 只在某个前缀范围内合并遍历；加一个写批处理，把多条写入合成一条 WAL 记录，减少 fsync 次数；加一个在线校验工具，定期扫描 SSTable 校验 CRC 并统计。这些都不改变核心结构，属于往上叠功能。

最后回到设计本身。这套引擎只有一千多行，但它把 LSM 的每个关键决策都摆到了明面上：为什么先写日志再改内存、为什么用跳表、为什么要有布隆过滤器、为什么必须合并、为什么删除要用墓碑。生产级数据库在这些点上做的选择大同小异，差别只在工程细节和参数调优。把这个迷你版跑通、把每个取舍讲清楚，再去看 RocksDB 或 LevelDB 的源码，很多当初看不懂的设计会一下子变得理所当然。

如果只能记住一句话，那就是：LSM 用「写放大换读放大、顺序写换随机写」这个交易，换来了极高的写入吞吐，而所有的复杂度——合并、墓碑、序列号、恢复——都是在为这笔交易付利息。理解利息付在哪里，就理解了整个引擎。

并发控制分两个层面。写入侧用一把写锁保护 MemTable 和 WAL 的追加，粒度尽量小：只锁住「追加记录 + 插入跳表」这一段，fsync 放到锁外异步做，否则所有写入都会排队等磁盘。读取侧完全不加锁，靠 MVCC 的快照序列号保证一致性。合并线程和前台写入之间用一个「不可变 MemTable 队列」传递，队列本身用通道实现，避免直接共享内存。把锁的边界画清楚，是这套结构能跑到十万级 QPS 的前提。

内存分配要留意 Go 的 GC 压力。跳表节点、WAL 缓冲区、读路径上的临时切片，都是高频分配点。几个实测有效的做法：WAL 缓冲区用 sync.Pool 复用；读路径上的迭代器复用同一个对象、每轮重置游标；把 key 的字节切片用 unsafe 的方式直接引用文件映射的内存，而不是先复制一份。改完这三点，GC 停顿从几十毫秒降到个位数毫秒，长尾延迟明显改善。

文件句柄管理容易被忽略，但会以「too many open files」的形式在半夜炸掉。每个 SSTable 打开时占一个句柄，合并时同时打开源文件和目标文件，句柄数会瞬间翻几倍。做法是维护一个句柄缓存（LRU，上限默认 512），超过上限就关闭最久未用的，用的时候再开。注意：关闭句柄不影响正在被迭代器引用的文件（迭代器持的是独立的读句柄），两者要分开管理，否则会出现「读到一半文件被关了」的诡异错误。

错误处理要区分「可重试」和「不可重试」。磁盘临时打满、文件被临时占用，属于可重试，退避重试即可；CRC 校验失败、魔数不对、索引偏移越界，属于数据损坏，不可重试，应当立刻上报并停止写入，避免在损坏之上继续叠加。最忌讳的是把两者都当成「打印个日志继续跑」——数据损坏时继续跑，会把损坏扩散到新生成的文件里，最后连备份都是坏的。

测试策略要分三层。单元测试覆盖编码解码、跳表、布隆过滤器、迭代器去重这些纯逻辑，跑得快、覆盖密。集成测试用「写入 N 条、重启、读回来」的循环，覆盖 WAL 重放和落盘。故障注入测试最值钱：在写入、落盘、合并的各个阶段随机杀进程，然后重启验证数据一致。这一层能抓出前面两层都抓不到的时序 bug。我们实现里就靠它抓到了「rename 前没 fsync 目录」的问题——文件本身 fsync 了，但目录项没落盘，断电后文件凭空消失。

性能剖析先用 pprof 定位，不要凭感觉改代码。典型结论往往是反直觉的：以为瓶颈在磁盘，profile 出来发现 60% 的时间花在 map 查找和内存分配上；以为瓶颈在 CPU，发现大量时间在等 fsync 的锁。做法是先跑基准、采 CPU profile 和 block profile，看火焰图里最宽的那一栏，改完再跑一遍对比。没有 profile 的优化，本质上是猜。

和 B 树对比能更清楚这套结构的定位。B 树是原地更新，读一次找一个节点，读延迟稳定且低，但每次写入要改页、要维护分裂与合并、并发控制复杂。LSM 是追加写，写延迟低、吞吐高，但读要跨多层文件、依赖合并来收敛，且删除是延迟的。选择的标准不是「哪个更先进」，而是「你的负载是读多还是写多、能不能容忍读延迟的抖动」。日志、时序、消息队列这类写多读少的场景，LSM 几乎总是更合适。

部署时要盯的监控指标不多，但每一个都要盯。写入侧：WAL 文件数量与总大小（持续增长说明落盘或合并卡住）、fsync 平均耗时（变长说明磁盘变慢）、MemTable 冻结频率（过高说明写入太猛或上限太小）。读取侧：块缓存命中率（低于 80% 要考虑加缓存或调热数据集）、平均与 P99 读延迟（两者差距拉大说明存在排队）。合并侧：待合并文件数（长期不为零说明合并跟不上）、合并耗时（变长说明数据量或磁盘在恶化）。

容量规划要留出三层余量。第一层是合并余量，前面说过，至少留「最大层容量的一倍」。第二层是 WAL 余量，WAL 在落盘前一直存在，写高峰时可能积压到几百 MB。第三层是快照余量，长事务持有的旧版本会推迟回收。三层加起来，磁盘使用率的安全水位建议不超过 70%。到 85% 就该告警，到 90% 合并很可能开始失败。

备份不能靠「复制文件」。SSTable 在运行时会新增、合并、删除，直接复制目录会拿到不一致的快照（比如复制到一半某个文件被合并删掉了）。正确做法是调用引擎自己的快照接口，让它把「当前所有活跃 SSTable + 当前 WAL 位置」记录下来，然后复制这份清单里的文件。或者更简单：定期做一次全量落盘（把 MemTable 刷成 SSTable）、暂停合并、复制、恢复合并。备份的复杂度来自「文件是活的」，不是来自数据量。

迁移到别的引擎时要算清成本。把 LSM 的数据导出给 B 树引擎，需要一次全量扫描，扫描期间要保证没有新写入（否则导出的是移动靶）。做法是先停写、导出、再切换。反向迁移（B 树导给 LSM）简单些，因为 LSM 只要求顺序写入，把源数据按 key 排序后顺序灌进去即可。无论哪个方向，都要在切换前用同一批查询在两边跑一遍、比对结果，不要只信「数据条数一样」。

读写放大的计算要落到具体公式上，否则「放大」只是个形容词。写放大 = 一份数据从写入到最终稳定，平均被重写了多少次。分层合并下，一份数据在每层都可能被重写一次，7 层意味着写放大接近 7 倍（实际因数据分布略有出入）。读放大 = 一次读平均要碰多少个文件。分层合并下，每层最多碰一个文件，所以读放大约等于层数。这两个数字此消彼长，调合并策略本质上就是在调这个比值。

再补几个容易配错的参数。block size 不是越大越好：读一个小 key 却拉进 16KB 数据，等于把缓存的有效容量缩小了四倍。bloom filter bits 也不是越大越好：每条 key 从 10 bit 提到 20 bit，内存翻倍，误判率只从 1% 降到 0.1%，而误判本来就只是多读一次磁盘、不影响正确性，多数场景不值。write buffer（MemTable 上限）调大能减少文件数，但会让恢复时间线性变长——64MB 对应恢复几百毫秒，512MB 对应几秒，要按「能接受多长重启时间」来定。

还有一个容易被问到的取舍：要不要把索引常驻内存。把每个 SSTable 的索引块全部加载到内存，读路径就不用为了索引再读一次磁盘，代价是内存占用随文件数线性增长。文件数上千、索引又大的时候，这部分内存可能比块缓存还多。折中方案是只常驻顶层（最新）几个文件的索引，旧文件的索引按需读。判断标准是「索引内存 + 块缓存内存」是否超过了给引擎的内存预算。

最后回答一个高频问题：这个迷你引擎能不能直接上生产。答案是不能，也不该。它缺了生产级引擎必备的几样东西：更精细的合并调度（按数据热度而不是按大小）、更完善的崩溃一致性验证（目录 fsync、双 WAL 等）、更细的并发控制（分段锁、无锁读路径）、以及大量的边界测试。但它是一个很好的教学载体，也是很好的「读源码前的预习」。把它的每一行都读懂、把每个参数都调过一遍，再去看成熟引擎的文档和源码，会顺畅得多。

把这套东西写完、跑通、测过之后，最实在的收获不是「我会写数据库了」，而是「我知道了数据库里那些参数为什么存在、调它们会牵动什么」。这种「知道取舍在哪」的直觉，是读多少篇介绍文章都换不来的。

合并迭代器的实现值得单独说。读一个 key 时要同时遍历多个来源：可变 MemTable、不可变 MemTable、以及每个 SSTable。做法是给每个来源起一个迭代器，把它们放进一个小顶堆，按「key 升序、同 key 按序列号降序」排序。每次取堆顶就是当前最小的 key 的最新版本；如果是墓碑就跳过，如果不是就把 value 返回。这个堆的大小等于来源个数，通常是个位数，开销可以忽略。合并迭代器写对了，读路径就基本正确了。

校验和（checksum）防的是「静默数据损坏」。磁盘会在多年后悄悄翻转几个 bit，读出来的数据看着正常、其实已经错了。CRC32 能发现这种错误，但发现之后怎么办是个问题：上报？跳过？用副本修复？我们的做法是上报并标记该文件为可疑，读请求返回错误而不是返回错数据。宁可报错也不要返回错数据——错数据会一路传到应用层、被写进别的地方，最后没人知道源头在哪。这也是为什么校验和不是可选项。

文件格式的版本兼容要提前留字段。footer 里除了魔数和索引偏移，还要留一段「格式版本号」和一段「保留字段」。第一版可能只有 8 字节保留，后面加 TTL、加压缩标识、加列族信息时，就往保留字段里塞。没有版本号的话，新版引擎读到旧版文件只能靠猜，一旦猜错就是数据事故。经验是：任何落盘格式，第一版就要带版本号和保留位，哪怕当时用不上。

单机多盘可以靠「按文件编号取模」把 SSTable 分散到不同磁盘，让合并的读写并行在不同设备上。要注意的是：同一个文件不能跨盘，否则一次顺序读会变成跨设备寻道。分配策略是「一个 SSTable 完整落在某一块盘上」，新文件的落盘位置按当前各盘的 I/O 队列长度选最空闲的。这样合并的读和写能同时打满多块盘的带宽，比单盘串行快接近盘数倍——直到 CPU 或内存成为新瓶颈。

可观测性接口要尽早接上。暴露一个 /metrics 端点输出 Prometheus 格式的计数器（写入条数、合并次数、缓存命中/未命中、fsync 次数）和直方图（读延迟、fsync 延迟），再暴露一个 /debug/pprof 端点按需采 profile。这两样东西加起来不到一百行代码，但省下的排查时间以天计。不要等出问题才临时加监控——出问题时你连「问题是何时开始的」都不知道。

MemTable 落盘要限速，否则会和前台写入抢 I/O。做法是给后台落盘线程一个令牌桶，每秒最多写 N MB，N 默认取磁盘顺序写带宽的三分之一。不限速的话，一次大落盘会瞬间占满磁盘带宽，前台的 fsync 全部排队，写入延迟从毫秒跳到几百毫秒，表现为「明明写入量不大，延迟却很高」。这类问题不看指标根本定位不到，因为 CPU 和内存都很闲，只有磁盘 util 是满的。

大 value 要单独处理。如果 value 动辄几 MB，把它和 key 一起塞进 SSTable 会让文件块变得极不均匀，索引和布隆过滤器的收益都被稀释。常见做法是把 value 拆到单独的 value log 文件里，SSTable 里只存「key + value 在 value log 中的偏移和长度」。这样 SSTable 保持小而整齐，读 key 快，读大 value 时才去 value log 取。代价是 value log 需要自己的垃圾回收。是否拆，取决于你的 value 大小分布：几百字节以内不值得拆，几 KB 以上就值得。

冷热分离能显著提升缓存效率。做法是给记录带一个「最近访问时间」，合并时把长期不访问的旧版本合并到更冷的层、甚至归档到单独的低速盘。热数据留在内存和顶层文件里，命中率高；冷数据留在慢盘上，几乎不占缓存。实现上不需要改核心结构，只在合并策略里加一条「按访问时间分层」的规则。收益在「热数据集远小于总数据量」的场景里最大，比如只查最近三个月、但要保留三年。

再补两个排查手法。第一，怀疑写入丢数据时，先对比 WAL 里的记录数和 MemTable 里的 key 数：正常情况前者略大于后者（含墓碑），如果前者明显小，说明写入根本没进 WAL，问题在写入路径而不是恢复路径。第二，怀疑读到了旧值时，把该 key 在各文件里的所有版本连序列号一起打印出来，按序列号排序看最新版本是不是被正确选中；如果最新版本是墓碑却返回了旧值，问题在迭代器去重逻辑。

还有一个实践建议：把「最坏情况」当成设计输入，而不是运行时的意外。磁盘会不会满？会。进程会不会被杀？会。机器会不会断电？会。合并会不会失败？会。每一项都要有明确的、写在文档里的行为约定，而不是「到时候再看」。这套引擎里所有的复杂度，本质上都是在为「最坏情况」买单；把这些最坏情况一个个想清楚、写下来、测过，引擎才算真的能用，而不是「跑起来看着没问题」。

收尾再说一句关于学习方法的事。读一篇讲 LSM 的文章，收获是「知道有这么回事」；自己动手写一遍、踩一遍坑，收获是「知道为什么只能这么设计」。前者会忘，后者会留下。这也是为什么这篇讲得这么细、把每个参数的后果都写出来——不是为了让你照抄参数，而是为了让你在别人给你一组参数时，能立刻说出「调大它会付出什么代价」。这种判断力，才是这套引擎真正想交付的东西。

日志与告警的阈值要按「能不能自动恢复」来分。能自动恢复的（合并重试成功、fsync 偶发变慢），记一条 warn 就够了，不要告警——否则告警会被噪音淹没，真出事时没人看。不能自动恢复的（CRC 失败、磁盘写满、恢复过程中发现文件缺失），必须告警，且告警内容要带上「哪个文件、哪个 key 范围、建议动作」。一条好的告警能让人五分钟内上手处理，一条坏的告警（只写「数据库异常」）只会让人去翻日志。阈值本身也要随基线调整，而不是写死。

测试数据要构造得有代表性，不能只用随机 key。随机 key 的分布均匀，恰好掩盖了真实数据里最常见的问题：热点 key（少数 key 承担大部分读写）、顺序 key（自增 ID，导致写入集中在文件末尾）、超长 key、以及大量重复 value。这四种模式各自能触发不同的问题——热点 key 让缓存失效、顺序 key 让合并产生倾斜、超长 key 撑爆索引、重复 value 让压缩虚高。基准测试里至少要有这四种数据集，报告里也要分开写，不要只报一个平均吞吐。

并发读的一致性要专门验。单线程读正确不代表并发读正确，因为迭代器在多个来源之间切换时，如果期间有合并删掉了某个文件，迭代器可能读到已经关闭的句柄或已经失效的偏移。验证方法是：起 8 个读线程持续扫全量数据、同时跑一个写线程持续写入和删除，跑半小时，断言每个读线程每次扫到的都满足快照语义（同一个快照序列号下，同一 key 的结果不变）。这一层测试不做，上生产后会在低概率下出现「读到了不该读到的版本」，而且极难复现。

开源实现的阅读顺序建议是：先读 LevelDB（结构最简单、代码量最小、概念最完整），把 WAL、MemTable、SSTable、合并这几块看一遍；再读 RocksDB（在 LevelDB 基础上加了列族、事务、限速、更多的合并策略），看它为了解决哪些生产问题加了什么；最后按需看专门领域的实现，比如为时序优化的、为内存优化的、为多机复制的。顺序反了容易一开始就被大量工程细节淹没，抓不住主干。

定期 scrub 是把「静默损坏」提前发现的唯一手段。做法是后台以低优先级、低速率扫描所有 SSTable 的每个块，重算 CRC 并和存储的校验值比对，发现不一致就把该文件标记为损坏、并触发一次针对该 key 范围的修复（从别的副本或备份取回）。scrub 的速度要能覆盖住磁盘的损坏速率，通常按「一周扫完一遍全量」来配置，且要限制它占用的带宽，避免影响正常读写。没有 scrub，损坏会在你真正需要那份数据的那天才暴露，而那时往往已经没有副本了。

升级与灰度要按「先兼容后切换」的顺序做。第一步是让新版本能读旧格式（向下兼容读），此时新旧版本可以混跑；第二步是让新版本写出的文件带新版本号，旧版本读到新文件时会明确报「版本不支持」，而不是猜着解析；第三步才是切换写入。跳过第一步直接升级，会出现「新版本写的数据旧版本读不了」，回滚时数据就尴尬了。任何落盘格式的变更，都要走这三步。

内存表与磁盘表的容量比例要有意识。MemTable 越大，能吸收的突发写入越多、产生的文件越少，但恢复时间越长、内存占用越高。经验比例是「MemTable 总量不超过给引擎内存预算的三分之一」，剩下三分之二留给块缓存和索引。如果 MemTable 占了一大半内存，块缓存被挤小，读命中率下降，读延迟会明显变差——表现为「写入很快但读取很慢」，根因却在内存分配上。

小数据量（几百 MB 以内）其实不该用 LSM。LSM 的全部复杂度都是为了解决「数据大到内存装不下、又要高写入吞吐」这个矛盾；数据小到能整体放进内存时，直接用内存里的有序结构或简单的哈希索引就够了，读延迟低、实现简单、没有合并的开销。把 LSM 用在小数据上是「用大炮打蚊子」：你付出了合并、恢复、墓碑这些复杂度，换来的写入吞吐优势根本用不上。技术选型的第一步永远是「先问数据量有多大」。

最后一条是沟通层面的：把你的设计决策和代价一起讲。说「我用了 LSM」没有信息量；说「我用了 LSM，因为写入是瓶颈、读延迟的抖动可以接受，代价是读要跨多层文件、并且要持续跑合并」才有。判断一个设计是不是真的好，不看它用了什么名词，而看它能不能把「为什么这么选、付出了什么」讲清楚。这套迷你引擎值得写下来、讲给别人听一遍——讲的过程里，你会发现自己哪一块其实是「照着抄的、没想明白」。
