# eval · 评测

> 「带评测与护栏」是这个项目的核心卖点之一 —— 这一目录就是它的实物。
> 不是「我觉得效果还不错」，而是**一批固定输入 + 可复算的指标 + 一个能重跑的命令**。

## 为什么这么设计

| 决定 | 为什么 |
|---|---|
| **直接 import 生产的消化链路**（`src/background/digest.js`） | 另写一份「评测专用调用」的话，分数反映的是那个副本，不是产品。对外说「准确率 90%」时，一问「评的是哪份实现」就穿了 |
| **正文存快照**，不每次现抓 | 网站改版、文章被删、登录墙变化，都会让「上周 87 分」失去意义。输入固定，分数才可比 |
| **跑分与打分分开**（`run.mjs` / `score.py`） | 改了金标准不用重跑模型 —— 打分是纯计算，随时可复算 |
| **金标准由人工确认** | 让模型自评自答没有意义。初标值只是给人工评审一个起点 |

## 目录

```
eval/
  dataset/
    cases.json        用例清单：链接、标题、金标准、备注
    texts/*.txt       正文快照（抓下来就不再变）
  fetch.mjs           抓正文快照（无头浏览器 + 生产的 content-script）
  run.mjs             跑分：逐条调用生产消化链路，产出 results.json
  score.py            打分：算指标、出报告（report.md）
  results.json        跑分原始产物
  report.md           评测报告
```

> **正文快照不在仓库里**（`.gitignore` 里排除了 `eval/dataset/texts/`）——
> 那是别人文章的全文，放公开仓库属于转载。
> clone 之后跑一次 `node eval/fetch.mjs` 就能重建：脚本、链接清单、金标准都在仓库里，
> 缺的只是那几份正文。**可复现的是机制，不是那几个文件的副本。**

## 怎么跑

```bash
# 前提：Ollama 在跑，且模型已拉取（见根目录 README 的安装步骤）

# 1) 抓正文快照（只抓缺的；--force 重抓全部）
node eval/fetch.mjs

# 2) 跑分（逐条调用生产链路，实测平均 12.3 秒/条；27 条 × 3 轮约 16 分钟）
node eval/run.mjs --repeat 3

# 3) 出报告
python eval/score.py
```

只想跑几条：

```bash
node eval/fetch.mjs --only life-sneeze,tech-skills
node eval/run.mjs   --only life-sneeze,tech-skills
```

## 加一条用例

1. 往 `dataset/cases.json` 的 `cases` 里加一条（`id` 唯一、`text` 指向 `texts/<id>.txt`）
2. `node eval/fetch.mjs --only <id>` 抓快照
3. 看一眼抓到的正文（**这一步不能省**：抓成导航垃圾的话，后面评的是模型对垃圾的反应）
4. 填 `expect`（金标准）

## 指标口径

| 指标 | 算法 | 为什么单列 |
|---|---|---|
| **分类一致率** | 与金标准一致 / 应消化的条数 | 主指标；`ok:false` 的条目不计入分母 |
| **误纳率** | 不该消化的却判成可消化的比例 | **比漏掉更糟**：用户会拿到一段凭空生成的摘要，而且看不出来。⚠️ 有多个口径 —— 报告用的是**模型侧**（能从本仓库复算的那个）；「模型是唯一防线」与「端到端」另算，不可混用 |
| **误拒率** | 该消化却被判 `ok:false` 的比例 | **和准确率同等重要**：用户已经付出等待成本，返回「无法处理」是零收益。这一项高说明护栏划错了边界 |
| **调用失败率** | 没跑出结构的比例 | 网络 / prompt 太苛刻导致反复校验不过 |
| **重试率** | 需要重试才通过的比例 | 反映 prompt 稳定性 —— 重试意味着单条成本翻倍 |
| **翻转条数** | 3 轮里时对时错的条数 | 信息量最大的一类：它精确指出「判据的哪句话没兜住」 |
| 耗时 | 平均 / 最长 | 本地 8B 模型的实际体感 |

## 已知限制（写清楚，别让人误读分数）

- **正文是快照**：提取用的是生产的 `content-script.js`，但「等正文稳定」的策略是评测脚本自己实现的
  （生产那份依赖 `chrome.tabs`，跑在 service worker 里）。所以它代表**消化质量**，不完全代表**抓取质量**。
- **抓取侧护栏完全不在链路上**：评测把正文直接喂给 `digestDocument`，绕过了 `digestAndStore` 的
  登录墙 / Cookie 墙判断。所以负样本这一节**只反映模型侧**的拦截能力；抓取侧要在真实浏览器里做端到端验证。
- **用例数偏少**：27 条，一致率只看趋势，不要当精确值（负样本那组更粗，6 条里单条就是 16.7 个百分点）。
- **要点完整性不含在内**：有没有漏内容需要人工判断，本报告不自动评。
- **单机**：模型有随机性（`temperature: 0.2`）。已做 **3 轮取多数表决 + 翻转条数 + Wilson 区间**，
  但换机器或换模型版本都要重跑才算数。

> `report.md` 里有一节「**评测覆盖不到的地方**」，逐条列出「为什么覆盖不到 / 在别处怎么验」。
