# WisdoMark

> 本地运行的**收藏消化助手**（Chrome MV3 插件）：读浏览器收藏或粘贴链接 → 抓正文 → 本地模型提炼「一句话摘要 + 核心观点 + 可行动清单」。
>
> 全本地，零云端。数据不出机器。

---

## 这是什么

收藏了一堆 AI Agent 学习内容，觉得有用但懒得看完，看完也总结不出东西 —— 于是全在收藏夹吃灰。

WisdoMark 把这个死循环拆掉：插件直接读你的收藏夹，用**本地 Ollama** 把每条内容压成一屏能看完的东西，并基于你已有的收藏反过来推断你的学习阶段，给出「接下来该做什么」。

**与「又一个剪藏 demo」的区别**：带**可量化的评测与护栏**。

| 指标 | 结果 | 说明 |
|---|---|---|
| 分类一致率 | **95.2%**（20/21） | 与人工裁决过的金标准比对；95% Wilson 区间 [77%, 99%] |
| 误纳率 | **16.7%**（1/6） | 不该消化的被消化了 —— 用户会拿到一段凭空生成的摘要，比漏掉更糟。唯一失手的 `neg-cookie` 已由抓取侧提前拦下（端到端 9/9），但**照样算进这个数**，详见报告 |
| 误拒率 | **0%**（0/21） | 该消化的内容没有被判成「无法处理」—— 这一项和准确率同等重要 |
| 调用失败率 | 0%（0/27） | 输出结构始终合法，没有跑不出 JSON 的情况 |
| 平均耗时 | 12.3 秒 / 条 | 本地 `qwen3:8b`，单机 |

上面这些回答的是「分类对不对、该拦的拦住了吗」—— 那是**门槛**。摘要有没写对才是**产品本身**，
所以另有一组指标拿**原文当标尺**去核它（[`eval/quality.md`](eval/quality.md)）：

| 摘要质量 | 结果 | 说明 |
|---|---|---|
| 漏条目（原文列 N 项却少写） | **0 / 5 条** | 产品最不能接受的失败 —— 用户以为看完了、其实漏了 |
| 数字幻觉率 | **2.8%**（1/36） | 卡片里的数字在原文找不到的比例。唯一那条是模型**自己数**出来的收录数，原文根本没写总数 |
| 空话措辞 | 0 处 | 对应 prompt 的明文禁令（「不许写『介绍了重要性』这类空话」）|
| 数字召回率 | 51.9%（40/77） | **偏保守的下限值**，只适合横向比 —— 模型把 N 条都写了但没写「N 个」也会算漏 |

> **27 条用例**：11 条来自真实收藏 + 10 条专打判据模糊地带的边界探针 + 6 条不该被消化的负样本（登录页 / 验证码页 / 404 / 导航页 / Cookie 声明页 / 加载中）；
> **每条跑 3 轮取多数表决**，翻转 0 条。金标准经三轮人工裁决。
> 跑的是**生产代码本身**（脚本直接 import 插件的消化模块），不是另写一份实现 ——
> 否则分数反映的是那个副本，不是产品。跑法见 [`eval/`](eval/README.md)，逐条明细与「这个分数覆盖不到什么」见 [`eval/report.md`](eval/report.md)。
> 数字对应 `prompt 1.12.0` · 2026-09-20（摘要质量一组为 2026-09-27 补测）。

## 它是怎么搭的

没有后端、没有数据库服务、没有云 —— 全在这台机器上，在这一个扩展里。

```
输入        收藏夹 · 粘贴链接 · 当前页面 · 批量(5~20 条)
             │
             ▼
抓取        content-script（按需注入，只读 DOM，不常驻）
            等正文渲染稳定再取 → 正文 + 图片清单
             │
             ├──► 正常正文 → 进入消化
             ├──► 图文帖（正文在图里）→ 侧栏离线 OCR，补进正文后再消化
             └──► 登录墙 / Cookie 声明页 / 正文过短 → 抓取侧直接拦下（不调模型）
             │
             ▼
消化        service worker（消息路由 + 落 storage）
            shared/prompt.json ────────► Ollama（本机 :11434）
            shared/output-schema.json ─► 结构校验 ──不合格──► 带着错误重试（≤3 次）
             │
             ▼
存储        全在本机，零云端
            IndexedDB 归档库：分类 + 摘要 + 要点（同链接去重 · 按时间分页）
               └─ 每条带 trace：耗时 · 模型调用次数 · 输入/输出 token
            chrome.storage.local：最近一次结果 / 画像 / 失败诊断日志（≤30 条）
             │
             ▼
消费        归档搜索 · 批量优先级 · 我的画像 · 接下来的行动清单
```

### 为什么这么拆

| 结构 | 为什么 |
|---|---|
| **护栏放在抓取侧**，不放模型 | 登录页、Cookie 声明页有**机械特征**，能一眼认出。能机械判的东西不该消耗一次模型调用，更不该指望 8B 模型判得准（实测它三轮都判错，还答得头头是道） |
| 分类判据 / prompt / 输出校验**只存一份**（`shared/`） | 插件和评测脚本读**同一份** JSON。分两份的话，评测分数只代表那个副本，不代表产品 |
| **判「内容形态」由代码做**，不交给模型 | 单一主题的清单和聚合类（周刊）的目标条数完全相反。实测交给模型时同一篇输出在 16~46 条之间跳；代码判完再明确告诉它，稳定在十几条、耗时减半 |
| **成功的 trace 挂归档记录、失败的进独立日志** | 归档库是用户资产（画像 / 批量 / 搜索都读它）。把失败记录混进去，那三个功能会把它当成一篇内容 —— 不报错，但结果悄悄变错 |
| **没有后端** | 数据不出机器、用户零安装、零费用。代价是受 MV3 限制（service worker 会被回收），所以长任务的编排放在侧栏页面里，SW 只负责「消化一条」 |
| OCR 引擎**随仓库打包**（5.6 MB） | 唯一一处「为了零安装而牺牲体积」的地方：识别图里的文字不能运行时去连 CDN，否则「全本地」就是假的 |

## 安装

> 当前处于**阶段 2（完整功能）已完成**：单条消化自动分类并落进本地归档库（同链接去重）；批量消化能排出优先级并挑出「本周必看 3 条」；「我的画像」能推断你在关注什么、现在到哪一步；「接下来做什么」把它落成能动手做的事；「归档」能把消化过的内容搜出来。

**1. 放行扩展来源（关键，跳过必失败）**

```bash
setx OLLAMA_ORIGINS "chrome-extension://*"
```

> `setx` 写入的是**用户级**环境变量，对已运行的进程无效 —— 执行后必须**完全退出 Ollama**（托盘图标右键退出）再重新打开。

**为什么必须做这一步**：Ollama 默认只放行 `localhost` 等来源，`chrome-extension://` 不在白名单里。它拦截的是**带 `Origin` 头**的请求，而浏览器只在跨源语义下才附加这个头 —— 插件探活用的 `GET /api/tags` 是简单请求、不带 Origin，所以显示「已连接」；一旦调模型（`POST` + `application/json`）带上 Origin，就必然被拒。**表现就是「状态灯是绿的，一消化就报 HTTP 403」**，很容易误判成模型或代码问题。

**2. 准备本地模型**

```bash
ollama pull qwen3:8b
```

验证：浏览器访问 <http://localhost:11434/api/tags> 应返回模型列表。

**3. 加载插件**

> Edge 与 Chrome 都是 Chromium 内核，用同一套 `chrome.*` API，步骤相同。

| 浏览器 | 扩展管理页 | 加载入口 |
|---|---|---|
| Edge | `edge://extensions/` | 左下角开「开发人员模式」→ 左上角「加载解压缩的扩展」 |
| Chrome | `chrome://extensions` | 右上角开「开发者模式」→ 左上角「加载已解压的扩展程序」 |

选中**本仓库根目录**（即含 `manifest.json` 的那一层，选文件夹本身，不要选里面的文件）。

加载后若工具栏没有图标：点工具栏的扩展图标（拼图）→ 找到 WisdoMark → 选「在工具栏中显示」。

点击 WisdoMark 图标 → 侧栏从右侧展开。

> Edge 已知问题：切到「之前开过侧栏」的标签页时，侧栏不会自动重新显示。这是 Edge 自身的行为，右键扩展图标选「在边栏中打开」即可。

## 使用

侧栏有五个入口：

| 入口 | 做什么 |
|---|---|
| **粘贴链接** | 粘贴任意 http/https 链接。会开一个**后台标签页**读正文，读完自动关掉；正文靠 JS 渲染的页面（知乎、掘金、小黑盒这类）会多等几秒等它出来。留空则消化当前页面。**点进输入框会自动全选**，直接粘下一条即可 |
| **最近收藏** | 读最近 20 条收藏，点任意一条直接消化 |
| **当前页面** | 消化正在看的这一页（另有「只抓正文」按钮，用于排查提取问题） |
| **批量** | 从一个收藏夹取 5～20 条，逐条消化后排出优先级 + 挑出「本周必看 3 条」 |
| **归档** | 把消化过的东西翻出来：搜关键词、按分类筛、点开看摘要与要点。**展开还能看到这一条是怎么来的** —— 用时多久、调了几次模型、进出各多少 token |

结果 = **分类徽标 + 一句话摘要 + 3～20 条要点**。条数怎么定，看这篇东西「讲的是不是一件事」：

| 内容形态 | 条数 | 例 |
|---|---|---|
| 单一主题的并列清单 | **跟着原文条目数走，一项不漏** | 一篇讲 11 个 skill 的文章 → 11 条以上 |
| 聚合类（周刊 / 日报 / 合集） | **按主题归纳**，一条里可以并列几个小条目 | 一期收录 28 篇内容的周刊 → 十几条 |
| 观点 / 分析 / 叙事 | 靠判断压缩 | 通常 3～8 条 |

**分类是自动的**，按「主题领域 → 你读完会去做什么」判定：

| 分类 | 什么内容会落在这里 | 例 |
|---|---|---|
| 技术学习 | 带**具体技术对象**（命令、代码、配置、参数、报错、性能数字）的知识与做法 | 教程、源码分析、技术复盘 |
| 工具与产品 | 某个工具能干什么、怎么用、值不值得用 | 软件推荐、插件测评 |
| 资讯与公告 | 事件本身，读完只需知道 | 版本发布、行业动态、跑分公布 |
| 游戏娱乐 | 一切以游戏为主题的内容 | 攻略、游戏更新公告、活动 |
| 生活常识 | 跟身体或过日子有关的科普与做法 | 健康科普、饮食、家居、消费 |
| 其他 | 以上都不是 | 职场、理财、情感、随笔 |

**要点随内容体裁变化**，不是一刀切的「3 个观点」：

| 内容体裁 | 要点是什么 |
|---|---|
| 观点 / 分析 | 核心观点 |
| 工具 / 应用 / 产品推荐 | 关键事实（推荐了什么、能力或参数、适用与限制） |
| 发布 / 更新公告 / 版本日志 | 关键变化（改了什么、影响什么、要做什么） |
| 教程 / 指南 | 关键步骤 —— **会写到能照着做**：具体命令、参数、路径、执行顺序，以及容易踩的坑 |
| 清单 / 合集 | 最值得关注的具体条目 |

> **长度由内容决定，不按规则卡死**：条数 3～20 条，单条上限 400 字。原文列了 11 项就写 11 条，一项都不能漏。信息装得下就少写几条，装不下就多写一条 ——
> 判断标准是「原文里用得上的信息有没有漏」，不是「够不够短」。压缩的对象是废话、寒暄和重复，不是信息本身；
> 一篇列了七个阶段的路线图，就该有七个阶段的信息，不能只写前三个。
>
> **「一篇讲 11 个 skill」和「一期收录 28 篇的周刊」要区别对待**：前者逐条跟随原文条目数（漏一项就是漏），
> 后者按主题归纳（一条里并列几个小条目是正常的，不叫漏）。
>
> 这个区别由**代码**判定，不交给模型 —— 看标题里的刊物特征（`周刊` / `第 N 期` / `合集` / `盘点` 这类词），
> 再把结论明确写进 prompt。实测交给模型自己判时，同一篇周刊的输出在 **16～46 条**之间跳，
> 还常常因超上限白跑一轮重试（41.6s → 74s）；明确告诉它类型之后稳定在十几条、30 秒出头。
>
> 这些上限定义在 `shared/prompt.json` 与 `shared/output-schema.json` 里 —— 同一份配置，插件和评测脚本共读。

只有**没有正文主体**的页面（登录页、错误页、导航页、只有 Cookie 提示）会被判定为无法消化并说明原因——这是设计内的护栏，不是报错。

> 反过来说：**内容体裁不是文章、主题与你的专业方向无关、信息量偏少，都绝不会导致拒收。** 收藏夹里的游戏公告、行业新闻、营销软文一样会被正常压缩。这条边界是实测踩过坑之后收紧的（详见 `AGENTS.md`）。

### 消化过的内容存在哪

每篇消化成功的文章都会写进**插件自己的本地归档库**（IndexedDB，扩展自带的存储，不上云、不需要额外权限）。结果下方会写一行账：

| 情况 | 显示 |
|---|---|
| 新的一篇 | `已归档 · 库中 12 篇。` |
| 之前消化过 | `这篇之前消化过，已更新归档（第 2 次 · 库中 12 篇）。` |
| 没存上 | `这次没能归档（原因）—— 摘要照样能看，但没进本地库。` |

**同一篇文章只会有一条记录。** 链接是从搜索页、分享面板还是收藏夹来的，带的跟踪参数都不一样，插件会先归一化再当去重键：

| 归一化 | 例子 |
|---|---|
| 剥掉跟踪参数 | B 站的 `?from=search&spm_id_from=…`、通用的 `utm_*` / `fbclid` |
| 剥掉锚点 | `/a#part-2` → `/a` |
| 统一协议与主机名大小写 | `http://` 与 `https://` 视为同一页 |
| 忽略末尾斜杠、归一参数顺序 | `/a/` 与 `/a`、`?a=1&b=2` 与 `?b=2&a=1` |

两处刻意的保守取舍：

- **参数过滤按域名限定** —— `from` 只在 B 站当来源标记剥掉；别的站点 `from` 可能有实际含义，不动
- **有内容的参数一律保留** —— `?id=1` 和 `?id=2` 是两篇文章。**漏合并只是让人看到重复，误合并会真的丢内容**，所以宁可少合并

模型判定「没有可消化正文」的页面（登录页 / 错误页）不入档 —— 存进去只会污染后面的画像。

> 这个库是「批量消化 / 画像推断 / 可行动清单 / 归档搜索」的共同地基 —— 没有历史记录，那四项都无处落脚。

### 归档：把消化过的东西翻出来

**「归档」**标签页：搜关键词（标题 + 摘要）、按分类筛、点标题展开看摘要与要点。展开是**瞬时**的，不必再等。

| 做法 | 为什么 |
|---|---|
| 搜索在**本地**做，不经过模型 | 关键词匹配没必要花 20 秒等模型。「按意思找」（语义搜索）是另一个量级的事，先不做 |
| 只搜**标题 + 摘要**，不搜要点 | 要点动辄几百字，把它也搜进去会让「正文里顺带提了一句」的内容大量命中 —— 噪音换来的召回不划算 |
| 摘要和要点**跟着列表一起回来** | 代价只是多传两项，而它们本来就是你要看的东西；换来的是点开即见 |
| 一页 30 条，**「继续往下看」**追加 | 库会越攒越大，一次全读出来的代价迟早会显出来 |
| 翻页的游标是 `[消化时间, 主键]`，不只是时间 | `Date.now()` 在**同一毫秒连续写多条**时会撞（批量消化就是连着写库），只按时间切页会整段跳过时间相同的那几条 —— 实测 35 条只翻出 34 条，而**少一条几乎没人会注意** |

> 阶段 1 落下的老记录还没有分类，会被归到「未分类」，用分类筛选能单独看到它们。

**分类体系改了怎么办？** 归档面板顶部会自动出现一行提示（「N 条还是旧分类体系」）+ 一个「重新分类」按钮：

- **只重跑版本落后的那些** —— 每条归档都记着「当时用的是哪一版分类体系」，重跑过就刷新。所以**中途停掉、下次接着跑不会重复处理已跑过的**
- 只想校正某一条：展开它，点「**重新消化**」
- 全量重跑要花时间（每条约 15 秒），提示里会写明大概要多久

### 这一条是怎么来的：消化过程的账

归档里点开任意一条，下面会多一行：

> 用时 12.3 秒 · 模型调用 1 次 · 输入 3,105 / 输出 480 token

- **「模型调用 2 次（重试过）」** —— 第一轮输出结构不合格，带着错误重问了一遍。这不是异常，是校验在起作用
- **输入 / 输出 token** 是 Ollama 报的**真实值**（不是估的）。长文慢是因为输入大，不是因为模型啰嗦
- 时间对不上时会补一句「其中模型侧 18.3 秒」—— 说明有一部分花在排队或网络上，而不是模型算得慢

**消化失败的也留痕。** 以前失败是静默的：报一句错就完了，之后再查不到它发生过 —— 是这一次还是每次都这样？是这一篇还是所有篇？无从判断。
现在归档页底部会出现一个可折叠的「最近有 N 次消化没拿到结果」，每条给：

| 给什么 | 为什么 |
|---|---|
| 错误原文 | 「连不上本地 Ollama」和「连续 3 次输出都不符合结构要求」要采取的行动完全不同 |
| **抓到多少字** | 分清「没抓到正文」和「模型不行」—— 一个要去改抓取、一个要去改判据 |
| 命中登录墙 / Cookie 声明页 / 正文过短 | 这三类是被**抓取侧护栏**拦下的，不是模型的锅 |
| 来源、调用次数、耗时 | 「只有批量消化才失败」这类问题，看来源最快 |

> 只记**「压根没拿到结果」**的。模型判定某一页没有正文主体**不算失败** —— 那是护栏在正常工作；
> 混在一起记，这个列表会被正常的护栏命中淹没，数字就没法看了。

> 失败记录**不进归档库**，单独存在别处。归档库是你的资产（画像推断、批量排序、搜索都读它），
> 把诊断数据混进去会让那几个功能悄悄算错。

### 批量消化：一次看一批，排出优先级

「批量」标签页可以一次取 5～20 条（默认 10）收藏，逐条消化后**横向排出优先级**，并挑出**本周必看 3 条**（每条附一句「为什么必看」）。

排序依据按重要性依次是：**相关性**（与你的方向贴不贴）→ **可操作性**（读完能不能立刻拿去做什么）→ **时效性**。

**结果分两块**：「本周必看 3 条」（每条附一句「为什么必看」，常驻显示）+「全部（按推荐顺序）」。

每一条都**默认收起，点标题才展开**看它的摘要与要点。一批十几条全铺开的话，面板会长到没法用，
反而找不到「该看哪条」。每条右侧有「原文 ↗」，不展开也能直接跳到原网页。

几个刻意的做法，都不是随手定的：

| 做法 | 为什么 |
|---|---|
| 编排跑在**侧栏**，不是 service worker | MV3 的 SW 空闲几十秒就被回收，而一批 10 条要跑 4 分钟左右。放在 SW 里，跑到第三条就断了 |
| 已消化的**直接复用归档**（30 天内） | 第二次跑同一批几乎不用等。批量要的是「横向排序」，不需要重读一遍原文 |
| 单条失败**不打断整批** | 10 条里坏 1 条，剩下 9 条照样该排序。失败的单列出来并说明原因 |
| 排序失败**也不白跑** | 内容都已经消化并归档了，这时退回按原顺序列出 |
| 中途可以**停** | 停在当前这条跑完之后 —— 不浪费已经花掉的模型时间，而且这条会顺带存进归档 |
| 收藏夹列表可以**手动刷新** | 那份列表只在第一次切到面板时读一次（每次切都重读太浪费）。你中途新建了收藏夹，点「刷新列表」就出来了 |
| 切到「批量」就**收起**单条消化的结果卡片 | 那张卡片是单条消化的产物，跟批量无关，留着会让人以为批量也出了结果。切回其他面板会自动恢复 |
| 批量**不写**「最近一次结果」 | 否则跑完一批再重开侧栏，只看到其中最后一条，会以为整批只消化了一条 |
| 结果卡片可以**收起** | 它常常有十几条要点，展开着会把下面的「我的画像」「本地模型」都挤下去。收起后标题右侧显示这是哪一篇，你的选择会被记住 |

> 10 条约 4 分钟（每条 20~40 秒，最后加约 20 秒排序）。已消化过的条目会被跳过，所以重复跑很快。
> **关掉侧栏不会丢进度**：已经消化的都进归档了，重新打开再点一次会从断点接着走。

### 我的画像：从你的收藏里看出你在关注什么

侧栏底部的「我的画像」会拿归档库里**最近 40 条**已消化的内容，推断出：

| 输出 | 是什么 |
|---|---|
| 关注方向 | 2~5 个，按比重排序，每个附一句说明 |
| 现在的位置 | 入门 / 进阶 / 实战 / 说不准 + 一句依据 |
| 倾向 | 偏理论还是偏实操 |
| 整体判断 | 两三句话：在往哪个方向走、看起来最缺什么 |

下面还会附一份**归档里各分类的条数** —— 那份是代码直接数出来的真实数字，
和上面模型给的定性判断**分开显示**，免得混为一谈。

几个刻意的做法：

| 做法 | 为什么 |
|---|---|
| 只喂「标题 + 分类 + 摘要」，不喂正文 | 判断「在关注什么方向」用摘要就够；几十条正文会撑爆上下文 |
| **数量、占比不交给模型** | 模型在计数上不可靠，而且算错了没人看得出来。数字一律由代码统计 |
| 位置拆成「枚举 + 依据」两个字段 | 实测：让模型自由写「一句话说明位置」，它永远只写两三个字（「进阶实践者」）。改成先选枚举、再写依据，它就跑不掉了 |
| 少于 5 条就不给结论 | 三五条内容推出来的「关注方向」纯属碰运气，而用户会把它当成事实 —— 这时明说「攒够再来」，而不是硬编一份 |

> 全流程本地完成，结果存在扩展自己的存储里，侧栏重开还在（不必重跑模型）。

### 接下来做什么：把画像变成能动手做的事

「我的画像」告诉你**你在关注什么**，「接下来做什么」回答的是**那我现在该干什么**。

它拿画像 + 同一批归档内容，给出：

| 输出 | 是什么 |
|---|---|
| 最该补的一块 | 一句话说清当前最缺的能力 |
| 3~5 条动作 | 按「先做哪个」排序。每条带**类型**（动手做 / 补一块 / 读一篇 / 整理）、**为什么是它**、**第一步怎么做** |

动作还会引用到具体的收藏，点标题直接跳原文 —— 清单的价值一半在「做什么」，
另一半在「拿什么做」。

几个刻意的做法：

| 做法 | 为什么 |
|---|---|
| 每条动作必须写出「第一步」 | 「加强 RAG 方面的学习」这种话没有信息量。要求细到「今天晚上打开电脑就能开始」：建什么文件、跑什么命令、查什么文档 |
| 类型用枚举（4 类），不是自由文本 | 模型写「学习类」这种自造分类时，界面上没法配颜色，也没法统计 —— 和分类体系是同一个道理 |
| 引用的条目序号**由代码过滤** | schema 只能校验「它是数字数组」，管不了范围。序号错一个就会指向不相干的内容，所以越界的一律丢掉：**宁可少给也不能给错** |
| 清单依赖画像，但不必先点画像 | 没有画像时后台会顺手算一份（并落库，画像卡片跟着就有了）—— 用户点的是「生成清单」，不该先被要求去点另一个按钮 |
| 条数门槛同样是 5 条 | 三五条内容提的「下一步」多半是套话。不够就明说「攒够再来」，不硬编一份 |

> 一次约 30 秒（没有画像时先生成画像，合计约 45 秒）。结果同样存在本地，侧栏重开还在。

### 正文写在图片里怎么办（图文帖）

B 站动态、小红书笔记、公众号长图这类内容的干货往往整段整段地画在图片里，DOM 里只有开场白。
**实测**那篇《零基础 AI Agent 学习路线图》：文字只有 1118 字（全是「大家好，今天我要讲七个阶段」），
七个阶段的划分、Track A / Track B 两条路线、每个阶段要用的工具全在 16 张图里 —— 只喂文字，模型只能写出一份空洞的摘要。

所以遇到「正文短 + 正文区大图多」的页面，插件会用**本地离线 OCR**（Tesseract，引擎在 `vendor/tesseract/`）把图里的字认出来，拼进正文再消化：

| 环节 | 做法 |
|---|---|
| 触发条件 | 正文 < 2000 字 **且** 正文区有 ≥2 张大图 —— 正常文章一张图都不会去识别 |
| 挑哪些图 | 短边 ≥200px、不宽扁（比例 ≤1:5）、不在页头页脚、URL 与 class 里没有 logo/avatar/icon/banner 之类的词，一页最多 **30 张** |
| 质量门 | 置信度 <55% 或字数 <8 的整张丢弃；和 DOM 里已有文字重复的也丢弃（图文帖常把正文再截一张图） |
| 上限 | 拼进正文最多 9000 字。识别过程中额度用满就停手 —— 后面的图认出来也会被截掉，继续认只是让你白等 |

结果下方会写明这一页的 OCR 账（几张图、认出几张、补了多少字）。实测那篇 B 站动态：
**1118 字 → 7378 字**（16 张图认出 14 张，补进 6260 字），摘要从「分为 Track A 和 Track B」
变成 6 条要点，把五个阶段、两条路线和避坑指南全列了出来。

> 识别一张图约 0.8 秒 —— 16 张实测 13 秒，这期间侧栏会显示进度。
> 封面那种「黑字压在带纹理的浅色背景上」的图会被置信度门挡掉（实测 33%）——它本来就只是标题，正文标题在 `document.title` 里已经有了。

展开「原始输出与重试明细」可以看到每次尝试的原始输出与失败原因。这份记录是为阶段 3 的失败分类留的。

## 故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 消化失败，提示 `Ollama 拒绝了扩展来源（HTTP 403）` | Ollama 未放行 `chrome-extension://` | 见「安装」第 1 步；改完环境变量必须**重启 Ollama** |
| 状态灯不绿、提示连接失败 | Ollama 没启动，或端口被占用 | 启动 Ollama；浏览器访问 <http://localhost:11434/api/tags> 确认 |
| 提示「**这个页面没抓到正文**」（只抓到几百字） | 正文靠 JS 渲染，抓取时还没出来 | 若这一页你自己打开能看到内容：**切到那个标签页，用「当前页面」入口重试** —— 手动打开的页面已经渲染好了，一定能抓到 |
| 提示「**这一页需要先登录**」 | 抓取侧认出这是登录 / 权限校验页（地址带登录标识、有密码或验证码输入框、正文全是登录话术） | 先在浏览器里登录好，再用「当前页面」入口重试；<br>如果它本来就只是个登录页，那没有内容可消化，忽略即可 —— **别去「切过去重试」，那条路走不通** |
| 提示「**这一页没有可消化的正文**」 | 模型判断这不是内容主体（登录页 / 错误页 / 导航页） | 检查抓到的字数：字数正常说明模型是对的；字数很少见上一条 |
| 后台标签页没自动关掉 | 页面加载超过 25 秒超时，或抓到的正文过少 | **是故意的**，方便你看到底加载出了什么，手动关掉即可 |

## 目录结构

```
manifest.json                    MV3 清单
LICENSE                          MIT（含随仓库打包的第三方组件许可清单）
shared/                          插件与评测脚本的单一来源
  prompt.json                      prompt 模板 + 模型参数
  output-schema.json               输出结构与校验规则
vendor/tesseract/                离线中文 OCR 引擎（约 5.6 MB，见其 README）
src/
  background/                    service worker（ES module）
    service-worker.js               消息路由
    shared.js                       加载 shared/、模板渲染、按 schema 校验
    llm.js                          Ollama 探活与调用（含错误分型）
    page.js                         抓正文（当前页 / 后台标签页）+ 图文帖判据
    digest.js                       消化流水线：解析 → 校验 → 重试 → 记 attempts
    trace.js                        诊断日志（成功的 trace 挂归档记录，失败的单独存）
    store.js                        本地归档库（IndexedDB + 同链接去重）
  content/content-script.js      按需注入，只读 DOM 抓正文与正文大图
  sidepanel/                     侧栏界面（html / css / js）
    ocr.js                          图片文字识别（离线，跑在侧栏）
    batch.js                        批量消化的编排（跑在侧栏，见上文说明）
```

`shared/` 是刻意的设计：prompt、调用参数、输出校验规则都只存一份 JSON，**插件和阶段 3 的 Python 评测脚本读同一份**。否则两套实现会让评测分数失去意义——分数只代表那个 Python 脚本，不代表插件。
